# Switching to the OpenCode Provider Likely Needs install_agent_hooks

`my-factory/city.toml.template` sets `provider = "claude"` and carries no
`install_agent_hooks` key. A student who switches that one line to `"opencode"`
gets a factory whose agents run, but which probably never installs the Gas City
OpenCode plugin — and nothing in the curriculum tells them so.

## What the provider setting controls

Verified against `gastownhall/gascity` at commit
`0b10e4e4d9648cdaf913193b3eed207e71bbdbb9` (v1.4.1).

`provider` selects the *harness* (which agent CLI runs). Resolution order, from
`internal/config/resolve.go` and `ApplyAgentDefaults` in `internal/config/config.go`:

```
agent.start_command (escape hatch)
  → agent.provider
    → rig override / patch
      → pack-scoped [agent_defaults].provider   (via InheritedProvider)
        → root city [agent_defaults].provider
          → [workspace].provider
            → hard error
```

There is no implicit default. With nothing set, `ResolveProvider` fails with
`provider is required; set agent.provider or workspace.provider to a key in [providers]`.

In this repository, `[workspace] provider` in `my-factory/city.toml` is the only
place it is set — no lesson pack agent under `packs/lessons/*/agents/*/agent.toml`
declares a `provider`, so all agents inherit the city value. One line switches the
whole factory.

Not to be confused with `[session] provider`, which selects the *runtime backend*
(`tmux`, `k8s`). The upstream docs flag this term as historically overloaded.

## The gap

Gas City ships genuine OpenCode support, including a plugin that supplies the
session lifecycle hooks:

- `internal/bootstrap/packs/core/overlay/per-provider/opencode/.opencode/plugins/gascity.js`
- installed to `.opencode/plugins/gascity.js` (`cmd/gc/cmd_start.go`)
- versioned and upgraded via `internal/hooks.opencodeHookVersion` /
  `opencodeHookNeedsUpgrade`

That plugin is what provides session-ID persistence, `gc handoff --auto` on
context compaction, and per-turn injection of `gc prime`, nudges, and unread mail.
Without it an OpenCode agent still runs but loses the lifecycle integration that
makes the factory coherent across turns.

`install_agent_hooks` is a `[workspace]` key that lists which providers get hooks
installed; `opencode` is an accepted value (`internal/config/config.go`). When
`gc init` is run with `--default-provider opencode`, it writes
`install_agent_hooks = ["opencode"]` into the generated `city.toml`. Our template
predates that path and was hand-authored, so it has no such key.

> [!question] UNDOCUMENTED
> Whether `install_agent_hooks` is strictly *required* for the OpenCode plugin to
> be installed, or whether `gc start` installs provider hooks regardless, is not
> established. The evidence is circumstantial: `gc init --default-provider opencode`
> writes the key, which implies opt-in, but the current template omits it entirely
> and the Claude path works. Resolve by running `gc doctor` and inspecting whether
> `.opencode/plugins/gascity.js` appears in the work directory, with and without
> the key. Do not state a requirement in student-facing text until this is settled.

## Constitutional status

Article IX (Reproducible Student Path): the documented path must work without
undocumented steps. A student following `installation.md` to OpenCode currently
gets a silently degraded factory with no indication anything is missing.

## Snapshot constraint on any fix

`test-harness/walkthroughs/L1.sh` line 111 copies `city.toml.template` **verbatim**
into the scratch city, sed-replaces only the city name, and snapshots the result at
line 186. Therefore **any** edit to the template — including a comment-only edit —
drifts `test-harness/walkthrough-snapshots/L1/city.toml`.

Consequences under Article IV:

- The snapshot MUST NOT be hand-edited to match.
- The L1 snapshot MUST be regenerated by a live run
  (`bash test-harness/tutorial-walkthrough.sh L1`) before the change ships.
- Line 119 of the same script asserts `formula_v2 = true` is present in the
  template; any edit must preserve it.

## Resolution taken

Superseded within the same session. The first pass added comment-only guidance while
the default stayed `claude`, on the reasoning that activating an unverified key on
the path every student uses would be speculative.

The default was then switched to OpenCode by explicit instruction, at which point
writing the key became well-founded rather than speculative: `install_agent_hooks =
["opencode"]` is exactly what `gc init --default-provider opencode` generates
upstream, so the template now matches the shape the tool itself produces. Final state
of `my-factory/city.toml.template`:

```toml
[workspace]
name = "my-factory"
provider = "opencode"
install_agent_hooks = ["opencode"]
```

`installation.md` was updated in the same change to state that the shipped default is
OpenCode and that the two keys must move together — otherwise the docs would recommend
Claude while the template shipped OpenCode, which is precisely the taught-vs-shipped
drift Article IV forbids.

The `UNDOCUMENTED` question above still stands: whether the key is strictly *required*
is unresolved. It is now known to be *correct*, which is a weaker but sufficient basis
for shipping it.

**Resolved (same session, later):** the `L1` blocker referenced below was fixed
(ADR-003 schema migration); `tutorial-walkthrough.sh L1` now passes and its
snapshot is current.

The original `UNDOCUMENTED` question — whether `install_agent_hooks` is strictly
required for the OpenCode plugin to install — is now answered empirically, not just
by inference from `gc init` output. Three live runs (L2 ×2, L3) all showed
`.opencode/plugins/gascity.js` present on disk with **no `install_agent_hooks` key
set anywhere** — not at workspace level (removed from `city.toml.template` this
session as deprecated) and not per-agent (never added to any `agent.toml`). `gc`
installs the provider's lifecycle hook automatically when the builtin provider
profile declares `SupportsHooks: true`, independent of this key. See
`vault/Discoveries/2026-08-17-architect-role-session-lifecycle-desync.md` for the
full live-run evidence.

**Conclusion:** do not add `install_agent_hooks` to the 19 lesson-pack `agent.toml`
files (P3, considered and closed). There is no evidence it is needed, and adding it
would be exactly the kind of unjustified, unverified config change Article XI
(Simplicity First) in the sibling repos' constitutions — and this repo's own minimum
-change discipline — warns against.
